# 技术方案 v1.0

> 对应需求文档：docs/需求文档-v1.md
> 一期范围：广州、深圳、佛山三地政务新闻 + 省级（可选）

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/后端 | Python 3.11 + FastAPI | 抓取、AI、API 同栈；异步性能足够 |
| 数据库 | SQLite（SQLAlchemy ORM） | 本地零配置起步；ORM 层保证后续换 PostgreSQL 只改连接串 |
| 抓取 | httpx + BeautifulSoup4 + feedparser | RSS/HTML 两种模式；httpx 异步并发 |
| 去重 | 归一化 URL 哈希 + 标题相似度 + SimHash（自实现，纯 Python） | 不引入重型依赖 |
| AI | OpenAI 兼容接口（openai SDK） | DeepSeek / MiniMax / 千问均提供 OpenAI 兼容 API，一套代码，模型可配置切换 |
| 队列/调度 | APScheduler（进程内定时）+ 后台任务队列（内存，可升级 Redis/Celery） | 几千条/天单机足够，架构预留升级点 |
| 前端 | 原生 HTML/JS + JSON API（前后端分离） | 无构建链；小程序二期直接消费同一 API |
| 认证 | 简单口令 Token（单用户） | 不开放注册 |

## 4. 三层去重设计

1. **URL 层**：去 query/fragment、统一 https、去尾斜杠 → sha256 → 查 `url_hash` 索引
2. **标题层**：去空白/标点归一化 → 同源内查 `title_hash` + 模糊相似度（difflib，阈值 0.9）
3. **正文层**：SimHash（分词 → 64 位指纹 → 汉明距离 ≤ 3 视为近似重复），同地域近 30 天记录比对

命中任一层 → 标记 skipped 并计入 fetch_log 的 duplicated。

## 5. AI 解读流水线

```
status=fetched 的新闻 → 分批(每批10条) → 并发调用 LLM
  → 单条提示词：输出 JSON {summary, key_points[], analysis, confidence, tags[], content_type}
  → 解析校验（JSON schema 校验失败重试1次）
  → confidence < 0.6 → review_status=pending（进复核队列）
  → status=interpreted；前端展示层即 published 视图
```

- 模型配置（.env）：`AI_PROVIDER=deepseek|minimax|qwen`，各 provider 预置 base_url，`AI_MODEL` 可指定
- 成本策略：优先全量用轻量模型；`content_type=policy`（政策文件）可配置用强模型（预留）
- 无 API Key 时：流水线跳过 AI，新闻照常入库浏览（保证本地先跑通）

## 6. 抓取器设计

- **RSS 源**：feedparser 解析，直取标题/链接/时间
- **HTML 源**：每源配置 `{list_selector, title_selector, date_selector, detail: {content_selector}}`，通用解析器执行
- 详情页正文抓取：二次请求 + `content_selector` 提取；失败降级为仅入库标题+链接
- 每源抓取独立 try/except，单源失败不影响其他源，写 fetch_logs
- 并发：asyncio.gather + 每源限速（礼貌抓取，1-2s 间隔）

## 8. 部署路径

- 本地：`uvicorn app.main:app --port 8300`，浏览器 http://localhost:8300
- 云服务器：同一镜像/代码，连接串换 PostgreSQL，systemd 托管 uvicorn + APScheduler 常驻

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 政府网站反爬/页面改版 | 每源独立配置+失败告警；礼貌抓取限速；选择器热更新（存库） |
| AI JSON 输出不稳 | schema 校验 + 重试 + 降级（仅摘要） |
| 政府站点无法从当前网络访问 | 先以可访问源验证链路，抓取器设计保持源无关 |
